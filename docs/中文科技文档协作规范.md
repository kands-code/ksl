# 中文科技文档协作规范

## 第一章 总则

### 1.1 目的

本规范用于统一项目中科技文档与代码注释的语言风格, 排版格式与协作流程,
保证内容在长期演进中保持一致, 准确, 易读, 并且对自动化工具与 AI Agent 友好.

### 1.2 适用范围

本规范适用于以下内容:

- 项目内的需求文档, 设计文档, 技术方案
- 用户手册, 开发者文档, API 文档
- 项目 README, 变更日志, 运维手册
- 代码注释与文档注释, 包括 rustdoc 与代码行注释
- 提交信息, 待确认事项等协作文本

代码标识符命名不在本规范范围内, 由相应的代码风格指南另行约定.

### 1.3 基本原则

1. 准确优先. 任何风格要求都不得损害技术内容的准确性.
2. 一致性优先. 同一术语, 同一格式在全部文档与注释中保持统一, 宁可选一个次优方案并贯彻到底, 也不要多人多法.
3. ASCII 优先. 除中文字符本身外, 标点与符号一律使用半角 ASCII 字符, 最大限度降低编码问题与工具链兼容风险.
4. 机器可读优先. 文档的主要读者与维护者是 AI Agent, 写法应当显式, 结构化, 无歧义, 便于程序解析与检查.

## 第二章 语言文字规范

### 2.1 中文用词规范

1. 一律使用简体中文, 用字以国家规范汉字表为准, 不使用繁体字, 异体字和已淘汰的旧字形.
2. 使用规范书面语, 不使用口语化表达和网络流行语.
   - 不推荐: 这个接口挂掉了.
   - 推荐: 该接口停止响应.
3. 避免使用含义模糊的词. 以下词语容易歧义, 应替换为明确表述:
   - 系统账号的登入动作一律写作登录, 不写作登陆.
   - 账号统一写作账号, 不写作帐号.
   - 表示抽象行为时用作, 如作为, 作出; 表示具体制造时用做.
4. 不使用生造词和音译词. 已有规范译名的术语必须使用规范译名.
   - 不推荐: 鲁棒性.
   - 推荐: 健壮性.
5. 同一概念在全文必须使用同一个词, 不允许为了避免重复而更换说法. 例如已选用配置文件, 就不要在后文写成配置文档或设置文件.
6. 技术文档以客观陈述为主, 谨慎使用我们, 大家等称呼. 推荐使用无主语句式或以您称呼读者.
7. 避免绝对化表述. 永远, 绝对不会, 百分之百等词语在技术语境下几乎总是不准确的, 应改为给出具体边界条件的描述.

### 2.2 英文原词与缩写的使用

1. 存在公认规范译名的概念, 使用中文译名. 例如: 数据库, 操作系统, 中间件, 负载均衡.
2. 没有合适的中文规范译名, 或者中文译名不如英文原词通行时, 直接使用英文原词, 不强行翻译. 常见情形包括:
   - 产品名, 项目名, 公司名: GitHub, Helix, tree-sitter.
   - 尚无通行译名的技术概念: Actor, Handler.
3. 英文原词的大小写以官方写法为准.
   - 正确: GitHub, Rust, macOS, tree-sitter.
   - 错误: Github, rust, MacOS, Tree-sitter.
4. 缩写词在全文首次出现时, 应先给出英文全称, 再说明后文使用缩写.
   推荐写法: 先写全称, 随后用一句独立的短句交代缩写, 或者用逗号引出说明.
   - 推荐: 执行模型采用续延传递风格. 下文统一简称 CPS.
   - 推荐: 检查器产出中间表示, 即 IR.
   - 不推荐: 续延传递风格 (CPS).
5. 缩写词一律使用大写原式, 如 API, SDK, HTTP, CPU, 不写作 Api, Sdk.
   复数形式直接加 s 或使用中文量词, 如多个 API, 不使用撇号.
6. 项目仓库维护一份术语表文件, 登记所有英文原词, 缩写与选定的中文译名. 术语表要求见第八章.

### 2.3 中英文混排

1. 中文与英文单词, 数字之间添加一个半角空格.
   - 正确: 使用 Rust 编写 ksl 解释器.
   - 错误: 使用Rust编写ksl解释器.
2. 英文单词与标点之间不加空格.
   - 正确: 运行 cargo test 之后, 检查测试输出.
   - 错误: 运行 cargo test 之后 , 检查测试输出.
3. 链接, 代码, 命令行等内容保留原始形态, 不强行在中西文之间补空格, 以可阅读为准.
4. 半角标点的空格规则见第四章, 优先级高于本条.

## 第三章 括号使用规范: 专项要求

### 3.1 总原则

行文中尽量避免使用括号进行补充说明. 括号会打断阅读节奏, 嵌套括号尤其损害可读性.
补充性内容应当通过改写句子, 调整结构或移出正文来承载.

### 3.2 禁止情形与改写方法

以下情形禁止使用括号, 须按给出的方法改写:

1. 解释词义. 不要在正文用括号夹注解释.
   - 不推荐: 调度器使用信箱 (一种消息队列) 保存待处理消息.
   - 推荐: 调度器使用信箱保存待处理消息. 信箱是一种消息队列.
2. 补充次要信息. 将补充内容拆分为独立句子, 或改用冒号, 逗号引出.
   - 不推荐: ReadKey 只在终端中可用 (标准输入不是终端时返回 NotATerminal).
   - 推荐: ReadKey 只在终端中可用. 标准输入不是终端时返回 NotATerminal.
3. 给出缩写或英文原名. 按第 2.2 条第 4 款处理, 使用独立短句或逗号说明.
   - 不推荐: 执行模型采用续延传递风格 (CPS).
   - 推荐: 执行模型采用续延传递风格, 其英文全称为 Continuation-Passing Style.
4. 罗列并列选项. 改用冒号引出, 或使用列表, 表格呈现.
   - 不推荐: 支持三种启动方式 (run, repl, lsp).
   - 推荐: 支持三种启动方式: run, repl, lsp.
5. 补充数据出处或参考. 改用脚注, 尾注或文末参考列表.

### 3.3 允许使用括号的情形

以下内容不属于行文补充说明, 允许使用括号:

1. 代码, 命令, 函数签名, 正则表达式, 数学公式中的括号, 属于语法本身.
2. 章节号, 列表编号等编号体系中的符号.
   同一文档内列表编号统一使用阿拉伯数字加点号的形式, 即 `1.`, 不使用带括号的编号, 以保持风格统一.
3. 直接引用他人原文, 且原文本身含括号时, 引用部分保持原样.

### 3.4 嵌套括号

任何情形下禁止括号嵌套. 遇到必须使用括号的合法内容, 而其中又需要引用说明时, 一律将说明拆出为独立句子或脚注.

## 第四章 标点符号规范: 统一半角

### 4.1 总原则

1. 全部行文统一使用半角英文标点, 与部分数学论文的排版惯例一致,
   目的是尽可能减少非 ASCII 字符带来的编码问题与工具链兼容问题.
2. 除中文字符本身外, 文档与注释中不应出现全角字符. 这包括全角标点, 全角空格, 全角字母与数字. 标点对照表中的禁用写法示例除外.
3. 代码块, 命令行, URL, 配置文件等内容保持原始形态, 不受本条约束.

### 4.2 标点对照

中文行文按以下对照表使用半角标点:

| 用途     | 禁用写法   | 规范写法                 |
| -------- | ---------- | ------------------------ |
| 逗号     | ，         | ,                        |
| 句号     | 。         | .                        |
| 分号     | ；         | ;                        |
| 冒号     | ：         | :                        |
| 问号     | ？         | ?                        |
| 顿号     | 、         | , 或改用列表             |
| 引号     | “” ‘’ 「」 | " 和 '                   |
| 省略号   | ……         | ...                      |
| 范围连接 | — ~        | -                        |
| 书名号   | 《》       | 使用引号或 Markdown 斜体 |

补充规则:

1. 并列词语之间原先用顿号的, 改用半角逗号, 例如: 词法器, 语法器, 类型检查器. 并列项超过三项或每项较长时, 优先改用列表.
2. 引号使用直引号. 外层引用使用双引号 `"`, 引号内再引用时使用单引号 `'`.
3. 不使用破折号. 需要补充说明时改用冒号引出或拆分为独立句子, 与第三章的括号规则保持一致的处理思路.
4. 书名, 文章名使用双引号或 Markdown 斜体标注, 例如: 详见 "ksl 语言设计". 文件名与代码实体优先使用反引号.
5. 不使用叹号表达强调. 技术文档依靠准确的措辞传递重要性. 确需提示风险时使用警告, 注意等提示块.

### 4.3 半角标点的空格规则

1. 半角标点与其后的文字之间添加一个半角空格, 例如: 构建完成后, 检查测试输出.
2. 半角标点与其前的文字之间不加空格.
3. 以下情形不受第 1 款约束, 保持紧凑写法:
   - 数字范围: 第 3-5 章, 10%-20%.
   - 时间: 14:30.
   - 版本号: v1.2.0.
   - 小数: 3.14.
   - 文件路径, URL, 代码实体内部.
4. 句末标点位于行尾时, 不再补空格.

### 4.4 符号的 ASCII 替代

1. 数学与技术符号优先使用 ASCII 等价写法: 乘号写作 `*` 或 `x`,
   箭头写作 ->, 温度写作 25 degC 或在行文中写 25 摄氏度.
2. 百分号与数字紧贴, 不加空格, 如 95%.
3. 不使用 emoji 和装饰性符号.

## 第五章 数字, 单位与时间

1. 技术参数, 统计数据使用阿拉伯数字, 如超时时间为 30 秒. 概数和习惯用语使用汉字数字, 如两种方式, 三四次重试.
2. 数字与单位之间加半角空格, 如 500 MB, 10 Gbps.
3. 计数文件, 版本, 章节等编号一律使用阿拉伯数字.
4. 日期统一写作 YYYY-MM-DD, 如 2026-07-19. 时间使用 24 小时制, 写作 HH:MM 或 HH:MM:SS.
5. 涉及金额时标明币种, 如 8000 元人民币.
6. 存储单位区分二进制与十进制. 内存容量使用 GiB, MiB,
   磁盘与网络带宽按厂商惯例使用 GB, Gbps, 全文遵循同一约定并在术语表中注明.

## 第六章 文档结构与排版

### 6.1 格式约定

1. 文档统一使用 Markdown 编写, 保存为 UTF-8 无 BOM 编码, 扩展名为 .md.
2. 换行使用 LF, 不使用 CRLF.
3. 每篇文档以一级标题开头, 一级标题即文档标题, 全文仅一个.
4. 标题层级不超过四级, 层级不得跳跃. 标题末尾不加标点.
5. Markdown 与 TOML 的格式由 `scripts/check-docs.sh` 检查, 提交钩子调用同一脚本.

### 6.2 段落与列表

1. 一段只讲一件事. 段落过长时按逻辑拆分, 优先拆分为列表.
2. 无序列表统一使用 `-`, 有序列表统一使用 `1.`.
3. 列表项为短语时末尾不加标点, 为完整句子时末尾加句号, 同一列表内统一.
4. 同类信息超过三项且存在多个维度时, 优先使用表格而非大段文字.

### 6.3 代码与命令

1. 行内代码, 命令, 文件名, 配置键名使用反引号包裹, 如 `Cargo.toml`.
2. 多行代码使用围栏代码块并标注语言, 如 ` ```rust `, ` ```bash `.
3. 命令示例应当可以直接复制执行. 需要读者替换的参数使用半角尖括号标注,
   如 `cargo run -p ksl-cli -- run <文件>`, 并在命令下方用独立句子解释各参数含义.
4. 示例代码必须保证可运行, 或在代码块上方明确标注: 以下为示意代码, 不可直接运行.

### 6.4 图片与链接

1. 图片统一存放在文档同级或项目统一的 assets 目录, 文件名使用小写字母与连字符.
2. 每张图片必须有替代文本, 说明图片内容, 服务于无障碍阅读与图片加载失败场景.
3. 链接文字应当描述目标内容, 不使用点这里, 此链接.
4. 引用外部资料时在文末列出参考来源, 正文中以脚注标注.

## 第七章 代码注释规范

### 7.1 语言与文字

1. 本项目统一使用中文注释, 用词遵循本规范第二章.
2. 中文注释同样遵循本规范的全部要求: 使用半角标点, 不使用括号补充说明, 术语与术语表一致.
3. 注释中除中文字符外不应出现全角字符, 防止源码编码异常与 diff 工具显示错乱.

### 7.2 内容要求

1. 注释只说明功能, 契约与不变量, 不复述代码字面行为, 不写项目变迁, 备选方案与讨论过程. 影响正确性, 并发安全或边界条件的实现原因可以保留.
   - 不推荐: `// 这里原先用递归, 后来改成显式栈`
   - 推荐: `// 使用显式栈, 避免长语句序列消耗调用栈`
2. 对外公开的 API 必须编写文档注释, 说明用途, 参数, 返回值, 错误语义与并发安全性等契约. 仓库内部 crate 的 `pub` 项只要求写清非显然约束, 不强制逐项补全契约.
3. 文档注释使用 Rust 的 rustdoc 格式, 便于工具提取生成文档.
4. 不保留被注释掉的代码. 历史版本通过版本管理追溯.
5. 注释必须与代码同步更新. 修改代码行为时必须检查并更新相关注释, 过期注释比没有注释危害更大.
6. 不在代码中保留 TODO, FIXME, NOTE, HACK 一类过程标记. 未完成事项与待确认问题记录在 `notes/roadmap.md`.
7. 自动生成的文件在头部注明生成工具与禁止手工修改的提示.

### 7.3 格式要求

1. 注释符号与注释文字之间加一个空格, 如 `// 注释内容`.
2. 行尾注释与代码之间的间距遵循语言官方风格.
3. 块注释每行宽度控制在 96 个半角字符以内, 超出时要在合适的位置换行.
4. 其余格式细节遵循 rustfmt 与项目 `rustfmt.toml` 的配置, 不手工调整.

## 第八章 术语与翻译管理

1. 项目仓库维护 `GLOSSARY.md`, 作为全部文档与代码注释用词的唯一依据.
2. 术语表条目包含: 英文原词, 缩写, 选定的中文译名, 是否允许直接使用英文, 备注.
3. 术语表采用 Markdown 表格维护, 保证机器可读.
4. 新术语引入流程: 在提交中同步新增术语条目, 随文档或代码一同合入, 不允许出现正文已使用而术语表未登记的术语.
5. 对已有术语的译名变更, 须提交独立的修改, 一次性更新全部受影响文件, 不允许只改一处造成新旧并存.
6. 拿不准是否有规范译名时, 按以下顺序查证, 若均无结果, 直接使用英文原词:
   - 全国科学技术名词审定委员会公布的术语
   - 国家标准与行业标准
   - 主流厂商官方中文文档
   - 业界通行译法

示例条目:

| 英文原词                   | 缩写 | 中文译名     | 允许英文原词 | 备注                     |
| -------------------------- | ---- | ------------ | ------------ | ------------------------ |
| Continuation-Passing Style | CPS  | 续延传递风格 | 是           | 正文直接使用缩写         |
| Actor                      | -    | -            | 是           | 并发原语, 不译           |
| Handler                    | -    | Actor 蓝图   | 是           | 运行时类型, 直接使用英文 |

## 第九章 Agent 协作流程

### 9.1 职责模型

1. AI Agent 是文档与注释的主要撰写者和维护者, 同时承担内容审校与语言审校双重职责, 通过自动化检查加自检清单完成质量把关.
2. 人类协作者作为最终决策者, 仅在以下节点介入: 需求确认, 方案取舍, 对外发布审批, 以及 Agent 主动上报的待确认事项.
3. 任何无法由规范直接覆盖的判断, **Agent 不得自行猜测后静默写入**, 应按第 9.5 条记录到 `notes/roadmap.md`.

### 9.2 完成定义

每次文档或注释变更在提交前必须满足以下条件:

1. 全文无行文括号, 无全角字符, 术语均已登记在术语表中. 标点对照表中的禁用写法示例除外. 文档与 TOML 用 `scripts/check-docs.sh` 检查格式, 注释标点由同一脚本检查.
2. 章节引用均为显式编号, 不存在上文, 前文, 如前所述等模糊指代.
3. 代码示例已验证可运行, 或已明确标注为示意代码.
4. 有 front matter 的受影响文档中 updated 字段已刷新.
5. 代码注释与本次行为变更已同步, 无过期注释.
6. 提交信息符合第 9.3 条约定.

### 9.3 提交与变更

1. 文档与代码同库管理, 使用相同的提交流程.
2. 提交保持原子性, 一次提交只做一件事. 术语变更单独提交.
3. 提交信息遵循 Conventional Commits 约定, 使用祈使句说明改动, 例如:
   - `docs: 补充 ReadKey 的终端限制`
   - `docs(readme): 修正示例运行命令`
   - `fix(comments): 同步 ReadKey 的过期注释`
4. 涉及行为变更的文档修改, 在提交说明中给出三段式摘要: 动机, 变更点, 影响面, 便于快速审阅.
5. 随功能交付的文档必须与功能在同一迭代内完成, 文档缺失视为功能未完成.
6. 文档默认允许直接修改, Git 作为历史备份, 非必要情况不保留修改前的内容.

### 9.4 面向 Agent 可读性的写作要求

1. 引用其他位置的内容一律使用显式章节号或文件路径, 如见第 3.2 条, 见 `docs/design.md` 第 14 节, 不使用依赖上下文的指代.
2. 每篇文档的关键约定在文内自洽, 不假设读者已阅读其他文档. 必要的前置知识以链接形式给出.
3. `docs/design.md` 只描述当前设计, 不记录决策过程, 备选方案与未来计划. 需要保留的远期方向与待确认问题写入 `notes/roadmap.md`.
4. 不确定的内容显式标注, 使用单独一行以待确认: 开头, 记录在 `notes/roadmap.md`, 如 `待确认: 终端原始模式的显式控制`.
5. 避免依赖排版暗示语义, 例如只用加粗表示重要而不说明原因. 语义应当由文字本身表达.

### 9.5 人类协作接口

1. 需要人类确认的事项集中记录在 `notes/roadmap.md`, 每条以待确认: 开头; 提交说明只列本次涉及的条目, 不散落在其他正文各处.
2. 人类协作者的评论, Agent 须逐条回应, 说明采纳, 不采纳及理由, 或补充修改.
3. 人类直接修改文档后, **Agent 在下一次变更前应先通读相关文档**, 确保后续修改建立在最新版本之上.
