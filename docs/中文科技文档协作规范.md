# 中文科技文档协作规范

## 1. 总则

### 1.1 目的与范围

本规范规定项目中科技文档与代码注释的语言, 排版与协作规则.

适用范围:

- 需求文档, 设计文档与技术方案.
- 用户手册, 开发者文档与 API 文档.
- README, 变更日志与运维手册.
- 代码注释, 包括 rustdoc 与行注释.
- 提交信息, 待确认事项等协作文本.

代码标识符命名由代码风格约定, 不在本规范范围内.

### 1.2 基本原则

1. 准确优先. 风格要求不得损害技术内容的准确性.
2. 一致优先. 同一术语与格式在全部文档中保持统一.
3. ASCII 优先. 除中文字符本身外, 标点与符号使用半角 ASCII 字符.
4. 显式优先. 写法应当结构化, 无歧义, 便于程序解析与检查.

## 2. 语言文字规范

### 2.1 中文用词

1. 使用简体中文与规范书面语, 不使用口语, 网络流行语与生造词.
2. 使用明确表述. 登录不写作登陆, 账号不写作帐号; 抽象行为用作为或作出, 具体制造用做.
3. 已有规范译名的术语使用中文译名, 例如健壮性, 不写作鲁棒性.
4. 同一概念全文使用同一个词, 不为避免重复而更换说法.
5. 技术文档以客观陈述为主, 使用无主语句式或以您称呼读者.
   不使用我们, 大家等称呼与绝对化表述.
6. 优先使用具体动词, 例如表示, 保存, 生成, 删除, 不使用承载, 收拢, 落地, 打通.
7. 不逐词直译英文复合词, 按中文习惯改写, 必要时登记到术语表.

### 2.2 英文原词与缩写

1. 有公认中文译名的概念使用中文译名, 例如数据库, 操作系统, 中间件.
2. 没有通行译名, 或英文原词比译名更通行时, 直接使用英文原词, 例如 Actor, Handler, tree-sitter.
3. 英文原词的大小写以官方写法为准, 例如 GitHub, Rust, macOS, tree-sitter.
4. 缩写首次出现时先给英文全称, 再用独立短句或逗号引出缩写.
   - 推荐: 执行模型采用续延传递风格. 下文统一简称 CPS.
   - 推荐: 检查器产出中间表示, 即 IR.
5. 缩写使用大写原式, 例如 API, SDK, HTTP, CPU. 复数直接加 s 或使用中文量词, 不使用撇号.
6. 项目术语表为 `docs/glossary.md`, 登记英文原词, 缩写与中文译名.

### 2.3 中英文混排

1. 中文与英文单词, 数字之间加一个半角空格.
   - 正确: 使用 Rust 编写 ksl 解释器.
   - 错误: 使用Rust编写ksl解释器.
2. 英文单词与标点之间不加空格.
3. 链接, 代码与命令行保留原始形态, 不强行补空格.
4. 半角标点的空格规则见第 4.3 节.

## 3. 括号

1. 行文尽量避免括号. 补充性内容改为独立句子, 冒号引出或列表.
2. 禁止用括号解释词义, 补充次要信息, 标注缩写, 罗列选项或给出数据出处.
   - 不推荐: 调度器使用信箱 (一种消息队列) 保存待处理消息.
   - 推荐: 调度器使用信箱保存待处理消息. 信箱是一种消息队列.
3. 允许使用括号的情形:
   - 代码, 命令, 函数签名, 正则表达式与数学公式.
   - 章节号与列表编号. 列表编号统一使用 `1.`, 不使用带括号的编号.
   - 直接引用原文, 且原文本身含括号.
4. 禁止括号嵌套. 必须说明时拆为独立句子或脚注.

## 4. 标点符号

### 4.1 规则

1. 行文统一使用半角标点.
2. 除中文字符本身外, 不出现全角字符. 标点对照表中的禁用写法示例除外.
3. 代码块, 命令行, URL 与配置文件保持原始形态.

### 4.2 对照表

| 用途     | 禁用写法   | 规范写法                 |
| -------- | ---------- | ------------------------ |
| 逗号     | ，         | ,                        |
| 句号     | 。         | .                        |
| 分号     | ；         | ;                        |
| 冒号     | ：         | :                        |
| 问号     | ？         | ?                        |
| 顿号     | 、         | , 或改用列表             |
| 引号     | “” ‘’ 「」 | " 和 '                   |
| 省略号   | ……         | ...                      |
| 范围连接 | — ~        | -                        |
| 书名号   | 《》       | 使用引号或 Markdown 斜体 |

补充规则:

1. 并列词语之间用半角逗号; 超过三项或每项较长时改用列表.
2. 引号使用直引号. 外层使用 `"`, 引号内再引用使用 `'`.
3. 不使用破折号. 补充说明改用冒号引出或拆分为独立句子.
4. 书名与文章名使用双引号或 Markdown 斜体; 文件名与代码实体使用反引号.
5. 不使用叹号强调. 风险提示使用警告或注意.

### 4.3 空格

1. 半角标点与其后的文字之间加一个半角空格.
2. 半角标点与其前的文字之间不加空格.
3. 数字范围, 时间, 版本号, 小数与文件路径内部保持紧凑.
4. 句末标点位于行尾时不补空格.

### 4.4 符号

1. 数学与技术符号优先使用 ASCII 等价写法, 例如乘号写作 `*` 或 `x`, 箭头写作 `->`.
2. 百分号与数字紧贴, 例如 95%.
3. 不使用 emoji 与装饰性符号.

## 5. 数字, 单位与时间

1. 技术参数与统计数据使用阿拉伯数字, 例如 30 秒; 概数与习惯用语使用汉字数字, 例如两种方式, 三四次重试.
2. 数字与单位之间加半角空格, 例如 500 MB, 10 Gbps.
3. 计数文件, 版本与章节等编号一律使用阿拉伯数字.
4. 日期写作 YYYY-MM-DD, 例如 2026-07-19; 时间使用 24 小时制, 写作 HH:MM 或 HH:MM:SS.
5. 涉及金额时标明币种, 例如 8000 元人民币.
6. 存储单位区分二进制与十进制. 内存容量使用 GiB, MiB, 磁盘与网络带宽按厂商惯例使用 GB, Gbps; 全文遵循同一约定并在术语表注明.

## 6. 文档结构与排版

### 6.1 格式

1. 文档使用 Markdown, 扩展名为 `.md`, 保存为 UTF-8 无 BOM, LF 换行.
2. 每篇文档以一级标题开头, 全文仅一个一级标题; 标题层级不超过四级, 不跳级, 标题末尾不加标点.
3. Markdown 与 TOML 的格式由 `scripts/check-docs.sh` 检查, 提交钩子调用同一脚本.

### 6.2 段落与列表

1. 一段只讲一件事, 段落不超过 4 句; 过长时按逻辑拆分, 优先改为列表.
2. 无序列表使用 `-`, 有序列表使用 `1.`.
3. 列表项为短语时末尾不加标点, 为完整句子时末尾加句号, 同一列表内统一.
4. 同类信息超过三项且存在多个维度时使用表格.
5. 正文换行落在分句边界, 首选句号与分号, 其次逗号; 不在短语中间断开.

### 6.3 代码与命令

1. 行内代码, 命令, 文件名与配置键名使用反引号, 例如 `Cargo.toml`.
2. 多行代码使用围栏代码块并标注语言.
3. 命令示例应可直接复制执行; 需要替换的参数使用半角尖括号标注, 并在命令下方解释各参数含义.
4. 示例代码必须可运行; 否则在代码块上方标注: 以下为示意代码, 不可直接运行.

### 6.4 图片与链接

1. 图片存放在文档同级或 `assets` 目录, 文件名使用小写字母与连字符.
2. 每张图片必须有替代文本, 说明图片内容.
3. 链接文字描述目标内容, 不使用点这里, 此链接.
4. 引用外部资料时在文末列出参考来源, 正文以脚注标注.

### 6.5 文档目录

1. 仓库根目录只保留 `README.md` 与 `AGENTS.md` 两个文档入口, 其余文档放在 `docs/` 下.
2. 文档文件名使用小写字母与连字符; `README.md` 与 `AGENTS.md` 保持大写.
3. `docs/` 顶层文档职责:
   - `about.md`: 项目定位与文档索引.
   - `tutorial.md`: 教程.
   - `roadmap.md`: 远期方向与待确认事项.
   - `glossary.md`: 术语表.
4. `docs/topics/` 按读者分族:
   - `language/`: 语言语义, 只写规则与边界.
   - `library/`: 内置能力, 只写清单, 签名与一句话说明.
   - `implementation/`: 实现架构, 工具与工程约束.
5. 清单类文档只写存在什么, 签名是什么, 用途与边界控制在两句话内. 语义规则与实现理由留在对应文档, 以文件路径指向, 同一事实不重复叙述.
6. 引用其他文档时写完整路径与章节号.
7. 内置能力目录的每个条目由签名行与描述行组成. 签名写作 `名字[参数名 : 类型, ...] : 返回类型`; 内置函数不加 `@`, 特殊形式加 `@`; 参数名只用于文档. ksl 没有柯里化.

### 6.6 信息增量与删改

1. 每句话必须有信息增量; 没有就删掉.
2. 优先删除, 其次改写, 不做无关重写.
3. 写怎么用, 边界与失败模式, 不复制实现细节.
4. 同一事实只在一处叙述, 其余位置给链接.
5. 清单类内容用列表, 存在多个维度时用表格.

### 6.7 禁用句式

1. 不写: 值得注意的是, 在本节中我们将, 综上所述, 总之, 可以看出, 需要注意的是.
2. 不写: 旨在, 通过……的方式, 为了确保……我们需要.
3. 不写: 有人可能会问, 假设用户……那么.
4. 不写: 虽然……但是为了健壮性, 如果不……就会……; 除非所述内容是真实的边界条件.
5. 不写 "本文档旨在介绍……"; 直接写用途, 配置, 用法与限制.

## 7. 代码注释规范

### 7.1 语言

1. 注释使用中文, 用词遵循第 2 章.
2. 注释遵循本规范的全部要求, 包括半角标点与括号规则.
3. 注释中除中文字符外不出现全角字符.

### 7.2 内容

1. 注释只说明功能, 契约与不变量, 不复述代码字面行为, 不写项目变迁, 备选方案与讨论过程.
2. 对外公开的 API 写清用途, 参数, 返回值, 错误语义与并发安全性; 仓库内部 crate 的 `pub` 项只要求写清非显然约束.
3. 文档注释使用 rustdoc 格式.
4. 不保留被注释掉的代码, 历史版本通过版本管理追溯.
5. 注释必须与代码同步更新; 过期注释比没有注释危害更大.
6. 不在代码中保留 TODO, FIXME, NOTE, HACK 一类过程标记. 未完成事项记录在 `docs/roadmap.md`.
7. 自动生成的文件在头部注明生成工具与禁止手工修改.

### 7.3 格式

1. 注释符号与注释文字之间加一个空格.
2. 行尾注释与代码的间距遵循语言官方风格.
3. 注释换行落在分句边界, 首选句号与分号, 其次逗号; 不在短语中间断开.
4. 注释每行不超过 96 个 Unicode 字符; 单句过长时先改写再换行.
5. 其余格式由 rustfmt 与 `rustfmt.toml` 决定, 不手工调整.

### 7.4 形态

1. 行内注释一般 1 至 3 行; 超过三行仍无新信息时删除或上移到模块文档.
2. 模块文档只写该模块的契约与不变量.
3. 前置条件直接陈述; 保留影响正确性, 并发安全或边界条件的实现原因, 以及副作用与失败模式.
4. 不确定的内容标 `待确认:`, 并按第 9.5 节记入 `docs/roadmap.md`.

## 8. 术语与翻译管理

1. `docs/glossary.md` 是全部文档与注释用词的唯一依据.
2. 术语表条目包含英文原词, 缩写, 中文译名, 是否允许英文原词与备注.
3. 术语表使用 Markdown 表格维护, 保证机器可读.
4. 新术语随文档或代码在同一提交中登记, 不允许正文已使用而术语表未登记.
5. 译名变更单独提交, 一次性更新全部受影响文件, 不允许新旧并存.
6. 没有规范译名时依次查证: 全国科学技术名词审定委员会术语, 国家标准与行业标准, 主流厂商官方中文文档, 业界通行译法; 均无结果时直接使用英文原词.

## 9. Agent 协作流程

### 9.1 职责

1. Agent 起草与维护文档和注释, 并做内容审校与语言审校.
2. 人类协作者负责需求确认, 方案取舍, 发布审批与待确认事项的决策.
3. 规范未覆盖的判断不自行写入, 按第 9.5 节记录到 `docs/roadmap.md`.

### 9.2 完成定义

变更在提交前满足:

1. 无行文括号, 无全角字符, 术语已登记. 标点对照表中的禁用写法示例除外. 格式由 `scripts/check-docs.sh` 检查.
2. 章节引用为显式编号或文件路径, 不使用上文, 前文, 如前所述等模糊指代.
3. 代码示例已验证可运行, 或已标注为示意代码.
4. 有 front matter 的受影响文档已刷新 `updated`.
5. 注释与行为变更同步, 无过期注释.
6. 提交信息符合第 9.3 节.

### 9.3 提交与变更

1. 文档与代码同库管理, 使用相同提交流程.
2. 提交保持原子性, 一次提交只做一件事; 术语变更单独提交.
3. 提交信息遵循 Conventional Commits, 使用祈使句, 例如 `docs: 补充 ReadKey 的终端限制`.
4. 涉及行为变更的文档修改, 在提交说明中给出动机, 变更点与影响面.
5. 随功能交付的文档与功能在同一迭代内完成, 文档缺失视为功能未完成.
6. 文档允许直接修改, Git 作为历史备份, 不保留修改前内容.

### 9.4 可读性

1. 引用其他位置时使用显式章节号或文件路径, 不使用依赖上下文的指代.
2. 每篇文档的关键约定自洽, 不假设读者已阅读其他文档; 必要的前置知识以链接给出.
3. `docs/topics/` 只描述当前实现与语言规则, 不记录决策过程, 备选方案与未来计划. 远期方向与待确认问题写入 `docs/roadmap.md`.
4. 避免依赖排版暗示语义; 语义由文字本身表达.

### 9.5 人类协作接口

1. 需要人类确认的事项集中记录在 `docs/roadmap.md`, 每条以 `待确认:` 开头. 提交说明只列本次涉及的条目.
2. 人类协作者的评论须逐条回应, 说明采纳, 不采纳及理由, 或补充修改.
3. 人类直接修改文档后, Agent 在下一次变更前先通读相关文档.

### 9.6 输出格式

1. 文档与注释的变更报告只输出三部分: 变更文件列表, 每文件一句话摘要, 待人工确认问题.
2. 待人工确认的问题至多 3 条, 按第 9.5 节记入 `docs/roadmap.md`.
3. 不输出分析过程与修改理由.

## 附录 A 速查表

| 场景             | 做法                                                |
| ---------------- | --------------------------------------------------- |
| 想补充解释一个词 | 拆成独立句子, 或移入脚注, 术语表                    |
| 想给缩写标注全称 | 首次出现写全称, 独立短句交代缩写                    |
| 没有规范中文译名 | 直接用英文原词, 登记进术语表                        |
| 中英文之间       | 加一个半角空格                                      |
| 标点             | 一律半角, 标点后加一个半角空格                      |
| 括号             | 仅语法本身允许, 行文补充一律改写                    |
| 日期             | YYYY-MM-DD                                          |
| 列表编号         | 统一使用 1.                                         |
| 模糊引用         | 改为显式章节号或文件路径                            |
| 代码注释         | 只写功能与契约, 与代码同步更新                      |
| 不确定的内容     | 单独一行以 `待确认:` 开头, 记录在 `docs/roadmap.md` |
| 句子没有信息增量 | 删掉, 或改写到能改变读者行动                        |
| 段落太长         | 拆为列表或多个段落, 每段不超过 4 句                 |
| 想说套话开场     | 直接写用途, 配置, 用法与限制                        |
| 注释在复述代码   | 删除, 或改写为约束与原因                            |
